# Gazebo simulation

Gazebo Harmonic (gz-sim 8) model of the coaxial TVC vehicle, plus the PX4 SITL
airframe config.

```
sim/
  models/tvc_vehicle/    the vehicle (SDF)
  worlds/tvc.sdf         ground plane + the vehicle, 1 ms physics step
  px4/4600_tvc_coax      PX4 SITL airframe -- READ ITS HEADER FIRST
```

## Run it

Inside the dev container (see [../README.md](../README.md)):

```bash
colcon build && source install/setup.bash
```

Bare Gazebo, no ROS — quickest check that the model loads and stands on its legs:

```bash
GZ_SIM_RESOURCE_PATH=$PWD/sim/models gz sim -r sim/worlds/tvc.sdf
```

Controller in the loop (replaces `simulator_node` with Gazebo on the same topics):

```bash
ros2 launch tvc_control gazebo.launch.py
```

Headless — **required on Windows and macOS hosts**, where the container has no
display:

```bash
ros2 launch tvc_control gazebo.launch.py gui:=false
```

Inspect what's happening without a GUI:

```bash
ros2 topic echo /sim/vehicle_attitude --once   # attitude Gazebo is reporting
ros2 topic echo /ctrl/gimbal_cmd --once        # what the controller commands
```

## What is real and what is approximate

**Calibrated from bench data** in the `tvc-data` repo:

- `motorConstant` 8.26e-6 — from 20.0 N max combined thrust at full throttle,
  measured in `raw/2026-07-20/loadcell/` (loaded by `tvctools.legacy`; those are
  the only runs that reach PWM 2000)
- `momentConstant` 0.016 — from the coax reaction-torque crossing in
  `out/pwm_thrust_torque_map.csv`
- Gimbal limits ±15°, slew 180°/s — matches `VehicleParams`, which matches the
  hardware's mechanical limit

**Geometry** is from `TVC Ver3.step`: gimbal pivot at the origin, rotors just
above, body stack up to +652 mm, three legs at −78 mm. Collision shapes are
simplified primitives (cylinders), not the CAD mesh — deliberate, since exact
collision meshes cost solver time and only matter on touchdown.

**Mass properties** are finalized in
[../docs/MASS_BUDGET.md](../docs/MASS_BUDGET.md) and regenerated by
`python tools/mass_properties.py tools/components.yaml`:

```
m = 1.3280 kg    CG at z = 211 mm    Ix = 0.0226  Iy = 0.0226  Iz = 0.00196
```

Link masses in the SDF sum to exactly 1.3280 kg. Structural parts use real
mesh-derived inertia from the CAD; electronics are located point masses.

**Still approximate:** the electronics *positions* are assumptions (748 g, more
than half the vehicle — the 307 g battery's assumed height moves the CG
noticeably). Treat attitude *time constants* as indicative rather than
predictive until the assembled vehicle is balance-tested, or a bifilar-pendulum
inertia measurement exists.

## Thrust margin

Max thrust is **20.0 N** against **13.03 N** of weight → **T/W ≈ 1.54**, a
workable VTVL margin. Hover sits at ~81% of max rotor speed
(`gazebo_bridge_node` computes and logs this).

That figure comes from the **2026-07-20** runs — the only ones reaching full
throttle (PWM 2000); every later session stops at 1850 µs. They drove both
rotors from one signal, i.e. the *balanced* case, which is the right basis:
unequal rotors make net roll torque, and roll is the one axis the gimbal cannot
trim. Three runs gave 18.07 / 19.34 / 19.96 N; 20.0 N is the optimistic end.

Corroborated independently: the 07-24 coax data, voltage-normalized to a fresh
pack and extrapolated to PWM 2000, predicts 17.8 N against 18.07 N measured —
agreement to ~1.5% across two different sessions and methods.

Full detail, including why an earlier 14.68 N / T/W 1.13 figure was wrong, is
in [../docs/MASS_BUDGET.md](../docs/MASS_BUDGET.md).

## PX4

`px4/4600_tvc_coax` configures **offboard direct actuator control** — PX4 does
state estimation, arming, failsafes, and logging while the attitude loop runs in
ROS2. This is a deliberate choice, not a limitation to work around: PX4's stock
control allocator assumes control torque comes from thrust *differences* across
fixed-direction rotors, but this vehicle gets yaw/pitch from *tilting one
thrust vector*, and its two rotors are nearly co-located. No combination of
`CA_*` geometry parameters expresses that.

The airframe file's header documents both paths, including what a custom
`ActuatorEffectivenessTVC` firmware module would involve if PX4's own attitude
loop is needed later. Start with offboard.

To use it, copy into a PX4 source tree and rebuild SITL:

```bash
cp sim/px4/4600_tvc_coax $PX4_DIR/ROMFS/px4fmu_common/init.d-posix/airframes/
```

Then add `4600_tvc_coax` to the `airframes` list in that directory's
`CMakeLists.txt`. PX4 itself is not in the dev container image — it is built
from source separately.

## Verified

Run headlessly in Gazebo Sim 8.14 inside the dev container:

```bash
bash sim/run_hover.sh --duration 25 --altitude 2.0            # hover
bash sim/run_hover.sh --duration 20 --record sim/hover.gif    # + video
python3 sim/plot_flight.py sim/flight_log.csv                 # + plots
```

Result: spawns tilted (pitch +10 deg, yaw -7 deg), recovers level in ~2 s,
then holds **2.00 m with 0.00 m drift and 0.0 deg tilt**, roll flat.

`run_hover.sh` starts the simulator **paused**, attaches the controller, and
only then unpauses. That is not cosmetic: the vehicle free-falls from its 2 m
spawn in ~0.6 s, so a controller attaching after an unpaused start finds it
already on the ground.

### Things that cost real debugging time

Recorded because each looked like a control problem and was not:

- **`OdometryPublisher` defaults to 2D.** Without `<dimensions>3</dimensions>`
  the message silently carries no `z` and no `vz`, so the altitude controller
  reads 0 forever and commands full thrust into the ground.
- **`gz` is a Ruby wrapper.** The real process has `comm == ruby`, so
  `pkill -x gz` matches nothing and dead simulators accumulate. Several of them
  publishing on the same topics feed the controller interleaved state from
  different worlds, which looks exactly like a physics instability.
  `pkill -f "gz sim"` is not the fix either: it also matches the shell running
  the script, which then kills itself.
- **Spawn height must clear the legs.** The lowest leg point is z = -0.171 m in
  the model frame; spawning below that starts the legs inside the ground plane
  and the contact impulse throws the vehicle over.
- **A perfectly upright spawn tests nothing.** The vehicle sits in equilibrium,
  the gimbal stays at exactly 0, and the plot looks flawless while proving
  nothing. The flight world is deliberately tilted.
- **Sign errors dominate.** Both the position loop and the roll differential
  were inverted at first; each turned its loop into positive feedback (roll
  reached -44 rad/s). Both signs are derived in comments where they are used.

### Still open

- **Takeoff from the ground** is not solved; `worlds/tvc.sdf` spawns on the legs
  but the hover demo uses the airborne world. Ground contact during spin-up is
  its own problem.
- **The ROS2 path** (`gazebo.launch.py` + `controller_node`) is written but has
  not been run; `hover.py` talks to Gazebo directly to avoid needing a colcon
  build. Expect to iterate on `ros_gz_bridge` type strings.
- **PX4 is not installed** in the container and is not needed for any of the
  above.

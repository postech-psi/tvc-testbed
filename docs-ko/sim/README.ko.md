# Gazebo 시뮬레이션

> 이 문서는 [../../sim/README.md](../../sim/README.md)의 한글 번역본입니다. 원본이 기준이며, 내용이 어긋날 경우 영문본을 따르세요.

동축 TVC 기체의 Gazebo Harmonic (gz-sim 8) 모델과 PX4 SITL 에어프레임 설정입니다.

```
sim/
  models/tvc_vehicle/    기체 (SDF)
  worlds/tvc.sdf         지면 + 기체, 1 ms 물리 스텝
  px4/4600_tvc_coax      PX4 SITL 에어프레임 -- 헤더를 먼저 읽으세요
```

## 실행

개발 컨테이너 안에서 ([README.ko.md](../README.ko.md) 참고):

```bash
colcon build && source install/setup.bash
```

ROS 없이 순수 Gazebo만 — 모델이 로드되고 다리로 서는지 가장 빠르게 확인:

```bash
GZ_SIM_RESOURCE_PATH=$PWD/sim/models gz sim -r sim/worlds/tvc.sdf
```

컨트롤러를 루프에 넣기 (같은 토픽 위에서 `simulator_node`를 Gazebo로 대체):

```bash
ros2 launch tvc_control gazebo.launch.py
```

헤드리스 — **Windows와 macOS 호스트에서는 필수**입니다. 그쪽 컨테이너에는 디스플레이가 없습니다:

```bash
ros2 launch tvc_control gazebo.launch.py gui:=false
```

GUI 없이 상황을 들여다보기:

```bash
ros2 topic echo /sim/vehicle_attitude --once   # Gazebo가 보고하는 자세
ros2 topic echo /ctrl/gimbal_cmd --once        # 컨트롤러가 내리는 명령
```

## 무엇이 실제이고 무엇이 근사인가

`tvc-data` 저장소의 **벤치 데이터로 보정된 값**:

- `motorConstant` 8.26e-6 — 풀 스로틀에서의 합산 최대 추력 20.0 N에서 유도. `raw/2026-07-20/loadcell/`에서 측정됨 (`tvctools.legacy`로 로드하며, PWM 2000에 도달하는 유일한 런들입니다)
- `momentConstant` 0.016 — `out/pwm_thrust_torque_map.csv`의 동축 반작용 토크 교차점에서 유도
- 짐벌 한계 ±15°, 슬루 180°/s — `VehicleParams`와 일치하며, 이는 다시 하드웨어의 기계적 한계와 일치합니다

**형상**은 `TVC Ver3.step`에서 가져왔습니다: 짐벌 피벗이 원점, 그 바로 위에 로터, 동체 스택이 +652 mm까지, 다리 세 개가 −78 mm에. 충돌 형상은 CAD 메시가 아니라 단순화된 프리미티브(원통)입니다 — 의도적인 선택으로, 정확한 충돌 메시는 솔버 시간을 잡아먹는 데 반해 실제로 중요한 건 접지 순간뿐이기 때문입니다.

**질량 특성**은 [MASS_BUDGET.ko.md](../MASS_BUDGET.ko.md)에서 확정되며, `python tools/mass_properties.py tools/components.yaml`로 재생성합니다:

```
m = 1.3280 kg    CG는 z = 211 mm    Ix = 0.0226  Iy = 0.0226  Iz = 0.00196
```

SDF의 링크 질량 합은 정확히 1.3280 kg입니다. 구조 부품은 CAD에서 유도한 실제 메시 기반 관성을 쓰고, 전자장비는 위치가 지정된 점질량입니다.

**여전히 근사인 것:** 전자장비의 *위치*는 가정입니다 (748 g으로 기체의 절반 이상 — 307 g 배터리의 가정된 높이가 CG를 눈에 띄게 움직입니다). 조립된 기체의 균형 시험을 하거나 이선 진자(bifilar pendulum) 관성 측정이 있기 전까지는, 자세 *시상수*를 예측값이 아니라 참고값으로 취급하세요.

## 추력 마진

최대 추력 **20.0 N** 대 무게 **13.03 N** → **T/W ≈ 1.54**로, 쓸 만한 VTVL 마진입니다. 호버는 최대 로터 속도의 약 81% 지점입니다 (`gazebo_bridge_node`가 계산해서 로그로 남깁니다).

이 수치는 **2026-07-20** 런에서 나왔습니다 — 풀 스로틀(PWM 2000)에 도달한 유일한 데이터로, 이후 세션은 전부 1850 µs에서 멈춥니다. 그 런들은 두 로터를 하나의 신호로 구동했습니다. 즉 *균형* 케이스인데, 이것이 올바른 기준입니다: 로터가 불균등하면 순 요 토크가 생기고, 요는 짐벌이 트림할 수 없는 유일한 축이기 때문입니다. 세 번의 런에서 18.07 / 19.34 / 19.96 N이 나왔고, 20.0 N은 그중 낙관적인 쪽 끝값입니다.

독립적으로 뒷받침됨: 07-24 동축 데이터를 새 팩 기준으로 전압 정규화하고 PWM 2000으로 외삽하면 17.8 N이 예측되는데, 실측값은 18.07 N이었습니다 — 서로 다른 두 세션과 두 방법이 약 1.5% 이내로 일치합니다.

이전의 14.68 N / T/W 1.13 수치가 왜 틀렸는지를 포함한 전체 내용은 [MASS_BUDGET.ko.md](../MASS_BUDGET.ko.md)에 있습니다.

## PX4

`px4/4600_tvc_coax`는 **오프보드 직접 액추에이터 제어(offboard direct actuator control)** 를 설정합니다 — PX4가 상태 추정, 시동, 페일세이프, 로깅을 담당하고 자세 루프는 ROS2에서 돕니다. 이건 우회해야 할 제약이 아니라 의도적인 선택입니다: PX4의 기본 제어 할당기는 제어 토크가 방향이 고정된 로터들 사이의 추력 *차이*에서 나온다고 가정하는데, 이 기체는 피치/롤을 *하나의 추력 벡터를 기울여서* 얻고, 두 로터는 거의 같은 위치에 있습니다. `CA_*` 형상 파라미터를 어떻게 조합해도 그것을 표현할 수 없습니다.

에어프레임 파일의 헤더에 두 경로가 모두 문서화돼 있으며, 나중에 PX4 자체의 자세 루프가 필요해질 경우 커스텀 `ActuatorEffectivenessTVC` 펌웨어 모듈이 무엇을 요구할지도 적혀 있습니다. 오프보드로 시작하세요.

사용하려면 PX4 소스 트리에 복사하고 SITL을 다시 빌드하세요:

```bash
cp sim/px4/4600_tvc_coax $PX4_DIR/ROMFS/px4fmu_common/init.d-posix/airframes/
```

그다음 그 디렉터리의 `CMakeLists.txt`에 있는 `airframes` 목록에 `4600_tvc_coax`를 추가하세요. PX4 자체는 개발 컨테이너 이미지에 들어 있지 않습니다 — 별도로 소스에서 빌드합니다.

## 검증됨

개발 컨테이너 안의 Gazebo Sim 8.14에서 헤드리스로 실행:

```bash
bash sim/run_hover.sh --duration 25 --altitude 2.0            # 호버
bash sim/run_hover.sh --duration 20 --record sim/hover.gif    # + 영상
python3 sim/plot_flight.py sim/flight_log.csv                 # + 플롯
```

결과: 기울어진 채로 스폰되어 (롤 +10도, 피치 -7도) 약 2초 만에 수평을 회복한 뒤, **드리프트 0.00 m, 기울기 0.0도로 2.00 m를 유지**하고 요도 평평합니다.

`run_hover.sh`는 시뮬레이터를 **일시정지 상태로** 시작해서 컨트롤러를 붙인 다음, 그제서야 정지를 풉니다. 이건 겉치레가 아닙니다: 기체는 2 m 스폰 지점에서 약 0.6초면 자유낙하하므로, 정지가 풀린 채로 시작한 뒤에 붙는 컨트롤러는 이미 땅에 떨어진 기체를 만나게 됩니다.

### 디버깅 시간을 실제로 잡아먹은 것들

전부 제어 문제처럼 보였지만 아니었기에 기록해 둡니다:

- **`OdometryPublisher`의 기본값은 2D입니다.** `<dimensions>3</dimensions>` 없이는 메시지가 `z`도 `vz`도 조용히 누락한 채로 전달돼서, 고도 컨트롤러가 영원히 0을 읽고 지면을 향해 최대 추력을 명령합니다.
- **`gz`는 Ruby 래퍼입니다.** 실제 프로세스의 `comm`이 `ruby`라서 `pkill -x gz`는 아무것도 잡지 못하고 죽은 시뮬레이터가 계속 쌓입니다. 그것들이 여러 개 같은 토픽에 퍼블리시하면 컨트롤러가 서로 다른 월드의 상태를 번갈아 받게 되는데, 이게 딱 물리 불안정처럼 보입니다. `pkill -f "gz sim"`도 해결책이 아닙니다: 스크립트를 실행 중인 셸까지 잡아서 스스로를 죽여버립니다.
- **스폰 높이는 다리보다 높아야 합니다.** 모델 좌표계에서 다리의 최하점은 z = -0.171 m입니다. 그보다 아래에서 스폰하면 다리가 지면 안에서 시작하고, 접촉 충격이 기체를 넘어뜨립니다.
- **완벽하게 똑바로 선 채로 스폰하면 아무것도 검증되지 않습니다.** 기체가 평형 상태에 있으니 짐벌은 정확히 0에 머물고, 플롯은 흠잡을 데 없어 보이지만 증명하는 건 아무것도 없습니다. 비행용 월드는 의도적으로 기울여 놓았습니다.
- **부호 오류가 압도적으로 많습니다.** 위치 루프와 요 차동이 처음엔 둘 다 뒤집혀 있었고, 각각 자기 루프를 양의 되먹임으로 바꿔놓았습니다 (요가 -44 rad/s까지 갔습니다). 두 부호 모두 사용되는 지점의 주석에 유도 과정을 적어두었습니다.

### 아직 미해결

- **지상에서의 이륙**은 해결되지 않았습니다. `worlds/tvc.sdf`는 다리로 선 상태에서 스폰하지만, 호버 데모는 공중 월드를 씁니다. 스핀업 중의 지면 접촉은 그 자체로 별개의 문제입니다.
- **ROS2 경로** (`gazebo.launch.py` + `controller_node`)는 작성돼 있지만 실행된 적이 없습니다. `hover.py`는 colcon 빌드를 요구하지 않으려고 Gazebo와 직접 통신합니다. `ros_gz_bridge` 타입 문자열에서 몇 번 시행착오를 겪을 각오를 하세요.
- **PX4는 컨테이너에 설치돼 있지 않으며**, 위의 어떤 작업에도 필요하지 않습니다.

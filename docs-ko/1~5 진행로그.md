## 1단계 — 컨테이너 빌드 (약 10분, 머신당 한 번)

### "Reopen in Container"가 정확히 뭔가

이름을 그대로 풀면 **"컨테이너 안에서 이 폴더를 다시 열기"** 입니다.
핵심은 **폴더가 바뀌는 게 아니라, VS Code가 명령을 실행하는 장소가 바뀐다**는 것.

```
[Reopen in Container 전]                [Reopen in Container 후]

  VS Code (내 맥)                         VS Code 창 (내 맥, 화면은 그대로)
    ├─ 편집기 → 맥의 파일                    ├─ 편집기 → 같은 파일 (바인드 마운트)
    ├─ 터미널 → 맥의 zsh                     ├─ 터미널 → 컨테이너의 bash  ← 바뀜
    └─ IntelliSense → 맥의 Python           └─ IntelliSense → 컨테이너 Python ← 바뀜
                                                   │
       ros2 → command not found                    └─ ros2 / gz / colcon 다 있음
```

**편집기 창은 똑같이 보입니다.** 파일도 같은 파일입니다
(`devcontainer.json` 의 `workspaceMount` 가 `type=bind` — 복사본이 아니라
맥 디스크의 그 파일을 컨테이너가 직접 봅니다). 바뀌는 건 **터미널·빌드·언어
서버가 실행되는 환경**입니다. 그래서 컨테이너 안에서 `ros2`가 되고,
맥 터미널에서는 안 됩니다.

### 클릭하면 내부적으로 벌어지는 일

```
① VS Code 가 .devcontainer/devcontainer.json 을 읽음
② 거기 적힌 dockerFile: "../Dockerfile" 로 Docker 가 이미지를 빌드
      FROM ros:jazzy              (Ubuntu 24.04 + ROS2 Jazzy 공식 이미지 다운로드)
      apt: cmake/ninja/colcon/rosdep/vcstool
      rosdep update               (ROS 패키지 매핑 인덱스)
      apt: gz-harmonic + ros-gz   (Gazebo 저장소 추가 후 설치)
      소스 빌드: Micro-XRCE-DDS-Agent v2.4.3   ← 10분의 대부분. 컴파일입니다
      pip: numpy scipy matplotlib pyyaml jinja2 empy
      useradd ros                 (root 아닌 사용자 생성)
③ 그 이미지로 컨테이너 시작 (이름: tvc-devcontainer)
④ VS Code 가 컨테이너 안에서 자신을 다시 열기
⑤ postCreateCommand 실행:
      sudo chown -R ros:ros /workspace
      rosdep install --from-paths /workspace/src
⑥ 컨테이너 안에 확장 설치: Python, C++, CMake, ROS
```

⑤의 `chown` 을 기억해 두세요 — **5단계의 git "dubious ownership" 문제의 원인**입니다.

`code` CLI가 없으니 둘 중 하나:

## 3단계 — ROS2 데모 실행 (2분)

- [x] 완료 (실행함 — `ros2 launch`는 계속 떠 있는 포그라운드 프로세스라 `Ctrl+C`로 직접 멈춰야 함. "안 멈춘다"는 느낌은 이 때문이며 정상 동작)

같은 컨테이너 터미널에서:

```bash
colcon build
source install/setup.bash
ros2 launch tvc_demo demo.launch.py
```

**세 줄이 각각 하는 일:**

| 명령 | 하는 일 | 다시 실행해야 할 때 |
|---|---|---|
| `colcon build` | `src/` 아래 **모든** 패키지 컴파일 (`tvc_demo`, `tvc_control`, `tvc_msgs`) | 패키지 **소스를 바꾸거나 추가**했을 때만 |
| `source install/setup.bash` | 이 셸에서 새 패키지를 찾을 수 있게 | **새로 여는 터미널마다 매번** |
| `ros2 launch tvc_demo demo.launch.py` | 퍼블리셔·서브스크라이버 두 노드를 동시에 띄움 | — |

`source` 를 매번 해야 하는 이유: 터미널 하나하나가 별개의 셸입니다. 환경변수는
그 셸 안에서만 살아 있습니다. **새 터미널에서 `package not found` 가 나면
거의 항상 이것입니다.**

**성공 화면** — 0.5초마다 번갈아 찍힙니다:

```
[counter_publisher-1]  [INFO] [...] [counter_publisher]: Publishing: 0
[counter_subscriber-2] [INFO] [...] [counter_subscriber]: Received: 0
[counter_publisher-1]  [INFO] [...] [counter_publisher]: Publishing: 1
[counter_subscriber-2] [INFO] [...] [counter_subscriber]: Received: 1
```

`Ctrl+C` 로 정지.

> README.ko.md 43행은 "1초에 한 번"이라고 적었지만, 실제 코드
> ([../src/tvc_demo/tvc_demo/counter_publisher.py](../src/tvc_demo/tvc_demo/counter_publisher.py))는
> `create_timer(0.5, …)` — **0.5초마다**입니다. 로그가 예상보다 두 배 빨리
> 찍히는 게 정상입니다.

**이 데모가 존재하는 이유:** 실제 물리 코드가 개입하기 전에 ROS2 파이프라인
전체(빌드 → 실행 → 토픽 → 메시지)가 작동한다는 걸 증명하는 것. 두 노드는
서로를 전혀 모르고 **토픽 이름 `/tvc_demo/counter` 만 공유**합니다. Phase 4의
실제 제어 노드도 똑같은 구조이고, 카운터 대신 기체 자세를 주고받을 뿐입니다.

- VS Code **Source Control 패널이 비어 있음**

으로 설정돼 있습니다. 컨테이너와 호스트는 **별개 환경**이라 신원이 공유되지 않습니다.

| 어디서 커밋할 건가 | 해야 할 일 |
|---|---|
| **호스트(맥)에서 커밋** ← 권장 | 아무것도 안 해도 됨. 이미 설정됨 |
| 컨테이너 터미널에서 커밋 | 컨테이너 안에서 `git config --global user.name/user.email` 별도 설정 |

기울기 0.0° 로 유지**, yaw 평탄.

**c. 헤드리스라서 데이터로 확인**

macOS에서는 GUI 창이 안 뜨는 게 정상입니다. 그래서:

```bash
ros2 topic echo /sim/vehicle_attitude --once   # Gazebo가 보고하는 자세
ros2 topic echo /ctrl/gimbal_cmd --once        # 제어기가 명령하는 짐벌 각
```

### 시작 전에 알아야 할 현재 상태

`sim/README.md` 와 `docs/ROADMAP.md` 가 정직하게 밝히는 것들입니다:

| 상태 | 항목 |
|---|---|
| ✅ 검증됨 | `hover.py` 경로. **단 Gazebo와 직접 대화** — ROS2 노드를 우회합니다 |
| ⚠️ 미실행 | **ROS2 경로** (`gazebo.launch.py` + `controller_node`) — 작성됐지만 한 번도 돌린 적 없음. `ros_gz_bridge` 타입 문자열에서 시행착오 예상 |
| ⚠️ 미설치 | **PX4** — 컨테이너에 없고, 위 어느 것에도 필요 없음 |
| ❌ 미해결 | **지상에서 이륙.** 호버 데모는 공중에서 시작. 스핀업 중 지면 접촉이 별도 문제 (다리가 유일한 접점, 기체는 높고 좁음) |

> **꼭 읽을 것:** `sim/README.md` 의 **"Things that cost real debugging time"** 절.
> 전부 *제어 문제처럼 보였지만 아니었던* 것들의 기록입니다. 예:
> `OdometryPublisher` 가 기본 2D라서 `<dimensions>3</dimensions>` 가 없으면
> 메시지에 `z` 가 조용히 빠지고, 고도 제어기가 영원히 0을 읽어 지면으로
> 풀스러스트를 넣습니다.

## 막혔을 때 — 증상별 대응

| 증상 | 원인 | 조치 |
|---|---|---|
| `ros2: command not found` | **컨테이너 안이 아님** (1순위 원인) | 왼쪽 아래 모서리 확인. 컨테이너 이름 없으면 `Cmd+Shift+P` → `Reopen in Container` |
| `package not found` (`tvc_demo`) | 새 터미널에서 `source` 안 함 | `source install/setup.bash` |
| 빌드가 중간에 실패 | 보통 다운로드 네트워크 문제 | 다시 `Reopen in Container`. **마지막 성공 레이어부터 이어서** 합니다 |
| "Docker daemon not running" | Docker Desktop 미시작 | Docker Desktop 실행, 고래 아이콘 애니메이션 멈출 때까지 대기 |
| Gazebo GUI 창이 안 뜸 | **macOS/Windows에서는 정상** (헤드리스) | `ros2 topic echo` / `plot_flight.py` 로 확인 |
| Source Control 비어 있음 / `dubious ownership` | `postCreateCommand` 의 `chown` 부작용 | 4단계 참조 |
| Dockerfile 고쳤는데 무변화 | 수정은 **다음 빌드** 때만 반영 | `Cmd+Shift+P` → `Dev Containers: Rebuild Container` |
| 컨테이너가 이상해짐 / 처음부터 다시 | — | `Cmd+Shift+P` → `Dev Containers: Rebuild Container` (레이어 캐시 덕에 1~2분) |

## 기억할 원칙 3개

1. **프로젝트 코드를 고치는 건 재빌드가 필요 없습니다.** 바인드 마운트라서
   저장하는 순간 컨테이너에 반영됩니다. **재빌드는 `Dockerfile` 을 고쳤을 때만.**
2. **`source install/setup.bash` 는 새 터미널마다 매번.** `colcon build` 는
   소스를 바꿨을 때만.
3. **컨테이너 안인지 항상 왼쪽 아래 모서리로 확인.** 안 되는 것의 절반이 이것입니다.
